# P1 red team — the refutation record

Three independent refuters were pointed at every new opinion constant this phase shipped, with one
instruction: **falsify it**. Perturb the number, delete the flag, replace the formula string with a
lie, and report what the repository does about it. Twenty-seven constants (or constant-shaped
records) drew forty-eight memos. This file is the record, committed with the phase.

**Why it is a file and not a paragraph.** The house rule is *constants need anchors*: a number
either stands on a measurement, or it ships flagged, gated and badged with the reason it cannot.
That rule is only worth what the audit behind it is worth, and an audit that leaves no trace is a
claim rather than a check. The memos below are reproduced **verbatim**, including the two places
where refuters disagree with each other, the places where a memo is wrong about the repository, and
every sentence critical of work this phase had just finished. Nothing was trimmed to look better.

## The verdict, and what changed because of it

A constant is **majority-unanchored** when more than half the refuters who attacked it returned
*unanchorable*. Eleven entries came back that way, covering **six distinct constants**. For each,
the question is the one V3-PLAN §6 asks: does the plan already say it *cannot be anchored* — in
which case its three legs (**gated + flagged in `constants` + labelled and badged in the Method
view**) must all actually hold — or does the plan claim an anchor that the red team has now refuted,
in which case the anchor is gone and no replacement may be invented.

|---|---|---|---|---|
| `sizing.min = 0.25` | 3 unanchorable / 3 | **claimed bounded** by "I44's domain sweep" | anchor **refuted** — the sweep is built *from* `SZ.min`, so it follows the constant wherever it goes | no replacement anchor invented. Flagged per §6's idiom: named in `constants.sizing.flag`, badged `estimate`, and **pinned** by new clause I44(e) — `sizingPrice(0.25) === 0.145` as a literal, the I41(b) idiom, which records the reviewed value and never justifies it |

legitimately flagged and bounded; none required an invented number, and no tolerance was widened
anywhere in this pass.

### Repairs the memos forced beyond the six

The red team found holes in constants that did *not* come back majority-unanchored. Those are fixed
here too, because a bound nobody can trust is worse than an admitted gap:

- **`sizing.ref === sizing.max === 1` is now asserted.** Four memos independently set `sizing.max`
  to 1.5 or 2 and shipped a domain admitting an **illegal super-pot 3-bet** with all 52 gates and
  the whole suite green, while I44's own report line narrated a window it had never swept. The
  pot-limit maximum being the reference is an arithmetic identity of the game; it was prose. I44(e)
  asserts it, and probes `s = 2` to prove the clamp bites.
- **`constants.rake.flag`'s presence and contents are gated.** Five memos deleted it and watched
  everything stay green while `stampConstants` republished the rake block *without* the admission —
  so the artifact shipped the one new opinion in the rake-depth coupling with nothing attached
  saying so. I41(g) requires it to exist and to name both `potScale` and the gate.
- **The limitations grep-gate is scoped to its own entry.** A refuter **swapped** the `n` values of
  limitations 16 and 17, leaving both notes byte-identical to METHODOLOGY.md, and passed all 52
  gates: `limitationProblems()` searched the whole flattened document and separately checked that a
  heading existed, so it never checked the note was *under* the entry it named — weaker than its own
  docstring promised. The search now runs over the slice from entry *N*'s heading to the next
  numbered entry and nowhere else. Relocating a note out of its entry fails too.
- **`flagsItExplains` is no longer decoration.** It is the only machine-readable link from a
  limitation to the flags that cite it, and it was deletable with everything green. Every path it
  declares must now resolve to a shipped constant in a block that actually carries a flag.

Every one of these clauses was **armed before it was believed**: twenty-three separate perturbations
— each flag deleted, each formula string falsified, each endpoint moved in both directions, the
badge map emptied, the limitation numbers swapped, the note relocated — and all twenty-three fail
the gate they were aimed at. The arming sweep is the reason these are checks rather than comments.

### The third leg, which is new

V3-PLAN §6 defines "flagged" as **named in `constants`, labelled in the Method view, and bounded by
a gate**. The third leg did not exist. The Method view walks `constants` generically, so
`rake.potScale` — the one new opinion in the rake-depth coupling — rendered as an ordinary field,
indistinguishable from the measured `potBB` beside it; five memos said so. `src/shell.html` now
carries an `UNANCHORED` map keyed by dotted path, and a flagged constant renders with an
`estimate` badge and a sentence saying what the badge means. It is asserted **from both sides**:
the gates read that map out of the source, so a flagged constant missing from it fails the build.

### Findings recorded, not acted on here

These are real and they are somebody's next job. They are named so they cannot be lost, not filed
as blockers:

1. **The `app` byte budget is effectively exhausted.** Three memos measured it: the page has grown
   344.8 → 359.7 KB against a 360 KB ceiling calibrated as "measured + ~5%", so the true headroom is
   about **0.3 KB, not 4.4%** — and this pass spent some of it on the badge. The next non-trivial
   shell change fails the build, and it will fail as a budget breach rather than as a considered
   raise. `docs/METHODOLOGY.md` §9.11 meanwhile names MODEL CODE as "the number to watch", which has
   ~11% clear. The watch line points at the wrong column.
2. **The layout-inclusive morph budget may be RED at HEAD.** One refuter ran `smoke.mjs` unmodified
   seven times on an Apple M5 Pro and failed the 4.0 ms budget every time (p95 13.7–17.2 ms),
   diagnosing a **cold sweep** rather than a slow page: the same 112 samples run twice give p95
   16.8–17.1 then 1.7–2.4, and a 3-second idle reproduces the anchor exactly. If that holds, the fix
   is a warm-up in the harness — *not* a bigger number, which would be tolerance-widening around a
   harness bug. It could not be reproduced in the session that wrote this file, because Playwright
   is not installed there and `smoke.mjs` cannot run at all. The finding is recorded in `smoke.mjs`
   beside the budget.
3. **`depth.beta`'s real bound is now I42(d), and METHODOLOGY does not say so.** Three memos
   measured it: I23(f) only required `|beta| < 1`, while I42's re-measured drift allowance and
   painted-sign clause together hold it to roughly **[0.15, 0.55]**. The depth→width gain adds no
   new constant — that claim survived every attack, including a smuggled `^1.02` — but it does give
   an existing, loosely-bounded constant a new consequence: before item 6b `beta` moved scores and
   realization; it now moves how many hands you open.
4. **The Method view's "Known weaknesses" list still does not read `constants.limitations`.** The
   two shipped admissions are published, byte-compared and badged — but as rows inside the constants
   dump, next to `nuBar`, rather than in the list a reader would look in for weaknesses.
5. **A limitation's `of` and `fix` fields are checked for existence, never against the document.**
   Only `note` is byte-compared, so the register's summary of what a limitation is *about* and what
   would fix it remains unbounded prose beside a gated sentence.
6. **§9.11's own caption contradicts itself**: it says all three byte budgets are "measured + ~5%",
   and forty lines later says the model-code gate is measured + ~8%. The 8% is deliberate and
   explained; the caption is what is wrong.

### rake.potScale = 1

> **Refuters:** 2 · **called unanchorable:** 1 / 2 · **majority verdict: anchored or legitimately bounded**

So the constant cannot drift silently, and the flagged+gated half of the contract holds for the NUMBER. But call the gate what it is: 2.00% and 0.2959 are potScale = 1 re-described through the same arithmetic, so I41(b) is a PIN, not an anchor - it proves the shipped exponent is the one that was reviewed, never that 1 is right, which is exactly what the plan claims and no more. Clause (d) recomputes the arithmetic using R.potScale itself, so it is self-consistent under any exponent and contributes nothing to the bound; clause (a)'s knee identity holds for every exponent because the ratio is 1 at d=100. The FLAG half is not gated at all: deleting `flag:` from the rake block leaves 52/52 gates and 436/436 tests green, and stampConstants then rewrites model.constants.rake wholesale so the admission also vanishes from the Method view - the page silently loses the sentence that legitimises the constant. Recommendation: add a clause asserting CONSTANTS.rake.flag is non-empty and names both `potScale` and I41, in the same grep-gate idiom I41(f) already uses for limitation 16.

**Refuter 2.** [falsifiable, unanchorable] Edited CONSTANTS.rake.potScale in a scratch clone to 1.5, 0.5, 1.001, 0.999 and -1, and re-ran all 52 gates plus the test suite. Separately deleted `rake.flag` (and `sizing.flag`) outright and re-ran verify.mjs, node --test and a full rebuild. -- The exponent is pinned tightly: potScale = 1.001 already fails I41 clause (b), because rakeFrac(250bb) drifts to 0.019982 against a hard-coded 0.02 held to 1e-15, and potScale = -1 additionally breaks clause (c)'s monotone-in-depth sweep at d=60 and d=80. So it moves nothing quietly. But clause (b)'s 2.00% and 0.2959 were themselves computed from potScale = 1, and clause (d) recomputes the arithmetic using R.potScale on both sides, so I41 is a PIN — it records the shipped value — not an anchor that tests it against an independent quantity. The plan is explicit that this is intentional ("bounded by gate I41 rather than justified"), and the knee identity does not help: potBB(100) = 60 holds for EVERY exponent, since the ratio is 1 at d = 100, so the identity anchors the form and says nothing about the exponent. The half of the gated + flagged + badged contract that actually fails is the flag: deleting `constants.rake.flag` from policy.mjs leaves all 52 gates passing, all 436 tests passing, and `build.mjs` regenerating a current artifact that ships potScale with no admission attached. The Method view renders `flag` only because constHTML walks every key of `constants` generically; no gate, test or grep asserts the key exists, and no rendering test asserts it reaches the page. Recommendation: add a one-line clause to I41 asserting `CONSTANTS.rake.flag` is a non-empty string naming both `potScale` and the gate — the same three lines I41(f) already spends on limitation 16, applied to the flag limitation 16 exists to explain.

### sizing.min = 0.25

> **Refuters:** 2 · **called unanchorable:** 2 / 2 · **majority verdict: CANNOT BE ANCHORED**

**Refuter 1.** [NOT falsifiable, unanchorable] Set sizing.min to 0.1, 0.05, 0.02, 0.01 and 0.001 in a scratch clone; ran the couplings family, the fixtures and policy-sweep families, the full `node scripts/verify.mjs`, and the full `node --test test/*.test.mjs`. -- Nothing falsifies this number downward. At sizing.min = 0.02 the run is 52/52 gates, 436/436 tests and `verify` exit 0; the same at 0.1, 0.05, 0.01 and 0.001. I44's domain sweep does NOT bound it, because the sweep is `[SZ.min, 0.4, 0.5, 0.6, 0.75, 0.9, SZ.ref]` - it reads the clamp as its own lower endpoint, so widening the domain simply widens the sweep and every clause (monotone narrowing, the exact price arithmetic, I15's two anchors) survives, since the price s/(1+2s) is smooth and monotone all the way to zero. The only direction that fails is UP: min = 0.6 fails I44(b) with `price arithmetic s0.4`, and that is an artefact of the gate's hard-coded probe points being clamped, not a claim about 0.25. The description 'a display clamp, not a threshold - no decision reads it' is also not quite true: envOf clamps `sizing` into [min, max] before anything downstream, so min is the value at which the model stops answering the question asked and starts answering a different one; it is a behavioural floor with no consumer that can see it move. Worse, there is no UI for the sizing axis at all - `src/shell.html` contains zero references to `sizing` beyond the legacy chip that still reads 'sizing is not modelled' - so 'display clamp' currently describes a display that does not exist. This is not a reason to invent an anchor, but I44 should assert the endpoint it claims to bound: e.g. that s < min is refused/clamped and that the domain is [min, max] with min < ref, so the number at least cannot move without a reviewer seeing it.

**Refuter 2.** [falsifiable, unanchorable] Moved CONSTANTS.sizing.min to 0.001, 0.05, 0.10 (downward, the direction the authored judgement points) and to 0.50 and 0.99 (upward), re-running all 52 gates and the full test suite at each value. -- The direction that carries the opinion is completely unguarded. sizing.min = 0.10, 0.05 and even 0.001 all ship with 52/52 gates green and 409/409 tests green — a 0.1%-of-pot "3-bet", priced at breakeven*0.003/1.002, is admitted by I44 without complaint, monotonicity intact and both I15 anchors holding. That is exactly the claim the constant is supposed to make ("below a quarter pot the face-up value range this node models is not the range anybody min-3-bets") and nothing in the repository tests it. Upward moves do fail I44, but for the wrong reason: the gate's probe list is `sizes = [SZ.min, 0.4, 0.5, 0.6, 0.75, 0.9, SZ.ref]`, so raising min to 0.50 leaves the literal 0.4 in the list, `envOf` clamps it, and the independently-recomputed price disagrees — "price arithmetic s0.4" is a clamp inconsistency in the gate's own fixture, not a statement about where the floor belongs. §6 records this constant as "bounded by I44's domain sweep", but I44 READS SZ.min to build its sweep rather than asserting anything about it, so the sweep follows the constant wherever it goes. A cheap fix that would give the clause teeth: assert a floor on the price or the continue width at SZ.min (e.g. that the modelled continue range at the lower clamp stays inside the band the face-up 60/25/10/5 mix can defend), so the clamp is bounded by the range model it claims to protect.
